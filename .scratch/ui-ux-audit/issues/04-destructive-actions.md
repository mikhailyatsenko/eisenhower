# Единая модель деструктивных действий

Type: grilling
Status: resolved

## Question

Сейчас подходы разные: удаление задачи идёт через `window.confirm`, у добавления есть toast с Undo, завершение (судя по `showToastNotificationByCompleteTask`) использует toast, «delete all» completed тоже через `window.confirm`, а удаление навсегда из Completed подтверждается ещё раз.

Какой единый принцип выбрать (undo-toast везде, confirm только для необратимого и массового, что-то ещё) и как он применяется к каждому из этих действий?

## Answer

**Принцип: отмена вместо подтверждения.** Действие выполняется сразу, в toast есть Undo. Подтверждение спрашиваем только там, где отмены нет.

| Действие | Как | Почему |
|---|---|---|
| Добавить, завершить, изменить задачу | toast с Undo (уже так). **Уточнено в [Поведение toast-уведомлений](12-toast-behaviour.md):** добавление и правка идут без toast, у завершения toast остаётся | обратимо |
| Удалить задачу (матрица и Completed) | **убрать `window.confirm`**, toast с Undo | `deleteTaskAction` уже умеет восстановить задачу на прежнее место |
| Переместить задачу в другой квадрант | **новый** toast «Перемещено в Schedule» с Undo | промах при перетаскивании — самая частая случайность |
| Сменить порядок внутри квадранта | ничего | иначе шум |
| «Delete all» в Completed | **свой** модальный диалог «Удалить 12 завершённых задач навсегда?», кнопки «Удалить» и «Отмена», Escape закрывает | необратимо: массив очищается, в облаке batch-удаление |

- Время жизни toast для удаления поднять с 2,5 до **6 секунд**: 2,5 мало, чтобы прочитать и нажать Undo, особенно на телефоне.
- `window.confirm` из приложения уходит полностью: он блокирует страницу и на телефоне выглядит как системная ошибка.
- Отменяемый «delete all» рассматривали и отклонили: нужно хранить снимок удалённого, в том числе в облаке, а операция редкая.

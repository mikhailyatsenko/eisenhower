# 09: Migration в пустой аккаунт

**What to build:** Анонимный пользователь с задачами входит в пустой аккаунт, и задачи сами переезжают в облако: матрица не меняется, toast «N tasks moved to your account» висит, пока пользователь не начнёт работать. Задачи устройства стираются только после подтверждения сервером, поэтому плохая сеть, закрытая вкладка или отказ облака не теряют и не задваивают их. Undo добавит тикет 10. Срез K [спеки R3](../spec.md), решения: [Модель «одна матрица»](../../ui-ux-audit/issues/03-one-matrix-model.md), [Офлайн для вошедшего пользователя](../../ui-ux-audit/issues/17-offline-ux.md) (строка «Migration»), [Поведение toast-уведомлений](../../ui-ux-audit/issues/12-toast-behaviour.md).

**Blocked by:** 08

**Status:** resolved

- [x] Migration нужна, когда пользователь вошёл, на устройстве есть задачи, которых нет в облаке (по id), и для этого `uid` не записан отказ (отказ появится в 10). Правило одно для входа кнопкой, входа в другой вкладке и пользователей, вошедших до R3.
- [x] Решение принимается, когда облако известно (снимок с сервера или из кэша устройства с задачами — то же условие, что снимает лоадер в R2). Облако «пусто», если в нём нет задач, кроме задач с этого устройства.
- [x] Чистая функция плана: задачи устройства (активные и Completed) + снимок облака → решение `none` | `move` | `ask`, N, `TaskChange[]`. Те же id, текст, `createdAt`, дедлайн, `completedAt`; порядок квадрантов сохраняется; задача с id, уже лежащим в облаке, не пишется. `ask` обрабатывает тикет 11, до него ничего не происходит.
- [x] `move`: одна запись через облачный клиент, задачи сразу видны в матрице из подписки; сразу toast «N tasks moved to your account» («1 task moved to your account»), N — все перенесённые, активные и Completed.
- [x] Toast Migration не гаснет через 6 с: висит до первого изменения матрицы (добавить, изменить, Complete, Delete, Move, Restore), смахивания или замены следующим toast. Выделение изменением не считается.
- [x] После `waitForPendingWrites` с устройства удаляются только задачи, которые есть в облаке по снимку с сервера. Все задачи устройства уже в облаке (вкладку закрыли до очистки) → очистка без toast.
- [x] Отказ облака — Sync error из R2; задачи остаются на устройстве.
- [x] Тесты. Seam 2 — таблица плана: облако пусто, облако с задачами, все уже в облаке, часть уже в облаке, только Completed, те же id. Главный seam (вход посреди теста — расширение `renderHomePage` и фейка): анонимный с 3 задачами входит в пустой аккаунт → те же задачи в матрице, `status` «3 tasks moved to your account», через 6+ с (fake timers) toast на месте, после Complete — исчез; в `serverTasks()` те же тексты; после Sign out матрица пуста; `stall` сразу после входа → toast есть, `reload()` до `goOnline` — ни дубля, ни вопроса, после `goOnline` на сервере по одной копии; `rejectNextWrite` на переносе → `alert`, после Sign out задачи устройства на месте; старт вошедшим с задачами на устройстве и пустым облаком → тот же перенос.
- [x] Чек-лист, раздел K: настоящий вход через Google с задачами на устройстве в пустой аккаунт; DevTools → Offline сразу после входа, перезагрузка, возврат сети — в консоли Firebase те же id, дублей нет; VoiceOver объявляет toast.

## Comments

**Что сделано.**

- **Слайс `features/migration`:**
  - `lib/migrationPlan` — чистая функция плана;
  - `types` — `MatrixTasks` и `MigrationPlan`;
  - `model/startMigration` — оркестратор на время входа;
  - `ui/Migration` — монтируется в `AppShell` рядом с `CloudMatrixSync` и по `uid` запускает и останавливает `startMigration`.
- **План.** Облако «пусто», если все его id есть на устройстве. Тогда решение `move`, задачи пишутся с теми же id и `order` = место в квадранте устройства. Задачи, уже лежащие в облаке, пропускаются. Если у облака есть свои задачи, решение `ask`: задачи устройства встают после облачных, Completed объединяется по `completedAt`. Этот случай посчитан сразу для тикета 11, а пока `startMigration` на `ask` ничего не делает. Если писать нечего, решение `none`.
- **Когда решается.** В `cloudSync` добавлен `listenToCloudSnapshots(listener)`: он передаёт каждый снимок и признак «облако известно» (`isKnownSnapshot`). Это то же условие, что снимает лоадер R2. `startMigration` решает один раз, на первом известном снимке.
- **Перенос.** `moveToCloudAction(changes)` делает одну запись через облачный клиент. Её учитывает sync model, диалог выхода считает её одной правкой. Задачи сразу приходят в матрицу из подписки, в том же снимке, что снимает лоадер, поэтому пустой матрицы между ними нет.
- **Toast.**
  - В `shared/ui/toast` появился `isPersistent`: у такого toast нет 6-секундного таймера, он уходит при смахивании или замене.
  - Гаснет при первом изменении матрицы через `listenToMatrixChanges`. Сигнал шлёт `writeToCloud`, через него проходят все действия вошедшего: добавить, изменить, Complete, Delete, Move, Restore, drag, Delete all. Сам перенос идёт мимо него, выделение ничего не пишет.
  - Дополнение: если облако отказало в переносе, toast гаснет, потому что задачи не переехали, а Sync error говорит об этом.
- **Очистка устройства.**
  - Порядок: `waitForPendingWrites`, затем первый снимок с сервера без pending (уже пришедший или следующий), затем `removeFromDeviceAction(id из снимка)`.
  - Отказанная запись уходит из снимка, поэтому её задачи остаются на устройстве.
  - Остановка при выходе или закрытии страницы отменяет очистку, ошибку ожидания (Firestore отклоняет его при смене пользователя) глотает. Задачи тогда остаются на устройстве, и следующий старт по правилу `none` их очищает.
- **Фейк облака.** Добавлен `cloud.stallNextWrite()`: сервер перестаёт отвечать ровно в момент следующей записи. Обычный `stall()` после клика «Continue with Google» опаздывает, потому что перенос уходит в тех же microtask-ах, что первый снимок сервера. `cloud` без `signedIn` уже задавал сервер для будущего входа, `signInWithGoogle` входит как `u1`/Ada, так что отдельная опция `lastUser` не понадобилась.

**Известные ограничения.**

- Настоящего входа через Google в сессии нет. Перенос, toast Migration и очистку в браузере не видел: их покрывают jest и чек-лист K.
- **Вход в другой вкладке.** Правило одно, но persist `tasksStore` не синхронизируется между вкладками: слушателя `storage` нет, и любое изменение стора записывает в localStorage копию этой вкладки. Вкладка, открытая, пока пользователь работал анонимно в другой, переносит свою устаревшую копию задач. Дублей нет, id те же, но задача, удалённая в первой вкладке, может вернуться в облаке, а правка текста — откатиться. Это ограничение всей анонимной матрицы, а не только Migration. Если нужно, стоит завести отдельный тикет на синхронизацию localStorage между вкладками.
- N после оборванного переноса считает только дописанные задачи, без уже лежащих в облаке. В обычном случае это все перенесённые.
- Пока нет Undo (тикет 10), на desktop toast Migration закрывает только изменение матрицы.
